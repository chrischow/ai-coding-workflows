# David Ondrej — Dexter's Agentic Engineering Workflow

[Link to video](https://www.youtube.com/watch?v=xgkjtF89-44)

David Ondrej interviews Dex (Dexter, "DexHorthy", founder of HumanLayer, inventor of the term "context engineering") about his agentic engineering workflow: why benchmarks don't matter, the software factory model, the "lights-off factory" failure, and his four-stage program design system.

## The software factory model

- The "software factory" has existed since the 1960s: a list of tasks (Jira, Linear), someone builds the thing, a PR, manual code review, CI/CD, prod, user feedback, monitoring (which wakes engineers at 3am).
- The first thing AI replaced is "person builds the thing" — this step went from hours/days to minutes/hours, while **code review stayed slow**. Every company now (Linear, WorkOS, Brex, Stripe) has some internal agent system doing this.
- Pre-AI, people fought the review bottleneck by spending hours in meetings to align on intent first, so the PR would match the shared understanding with fewer required changes. You can spend an hour up front to save hours in review and avoid building the wrong thing.
- To compress review speed you throw agents at it: agent code review (catches the small stuff), browser testing, app poking. But reading code — or building trust that the code is right today and won't slow you down in a month — remains the bottleneck. You cannot manually review tens of thousands of lines.
- Trust-building: "Codex and Opus both found 10 things, we fixed all 10" → you don't get woken up at 3am. You can also route incidents and support tickets straight into the factory: instead of waking up to an alert, you wake up to a pull request.
- Dex's own implementation: GLM 5.2 reviews every uptime incident for his API (Deep API). Incidents go through a loop on Render.com with cron jobs on Vercel and GitHub Actions; he gets an AI report ("this is the provider, nothing we can do" or "caused by a missing migration — do this") and a draft message for the Discord channel.

## Why the "lights-off factory" fails (read the code, or at least know the logic)

- The tempting endpoint is a factory where humans never read code: agents test changes live, send video demos, agent code review, regression testing that permanently kills failure modes, stronger CI/CD, more linters, complexity monitoring. Your job becomes "how many features can you ask for?"
- Dex's thesis: **this doesn't work today**, and if you stop reading code you lose the touch of the codebase — eventually hitting a bug no agent can fix, even with three frontier models in a council repeatedly shipping non-fixes. Then you must trudge through months-old sloppy code for days or weeks.
- He lived it: in July 2025 they ran a "lights-off factory" (reviewing plans and tickets but not code) shipping a desktop app. They hit a bug; users were pissed; they spent miserable weeks reading "slop code". The odds that stopping reading code bites you are much higher than the models getting smart enough to save you by then.
- One refinement: it's less about reading *code* than understanding **logic/product** — the API schema you use, concepts like hashing vs encryption, what the first five minutes of onboarding look like, what happens when a user cancels, what happens when an endpoint fires. Know what the product is.

## The four-stage design system (Dex's program design)

The antidote: spend small amounts of up-front attention, in the right order, to keep the human in the loop and let the agent "cook" on what it's good at. No special tool required.

1. **Product** — What user problem are we solving and how do we measure it? If you can attach a measurable output (a number on your site tied to conversion, revenue, users), "the agent will move mountains for you" (the same idea as auto-research: "make this CUDA kernel faster until 20% resource reduction"). Newer models self-test more — e.g. switching an LLM provider, they'll check cost/speed/quality with an LM-as-judge without being told — but deterministic numbers (experiments, A/B data checked daily) are far more powerful.
   - Example: a PRD built in HumanLayer with problem statement, success metrics, and the Amazon trick — **write the blog post before you build the feature**, so you think through how you'll explain it and why it's valuable before any code. Plus HTML mockups of every relevant view, iterated on, with no tech/architecture/databases involved.
   - People say this is extra work, but 20 minutes up front raises the odds the agent ships something that doesn't need hand-polish. And models will happily let you churn for days with zero progress and zero users without calling you out.
2. **System architecture** — How services fit together, the flow, new endpoints, new tables, outlines of queries. One level down; a lot of people already do this with models. A caveat: there are times to vibe-code — if you're pre-product-market-fit, throw things at customers and find what they'll pay for; this process is for teams (~5+ engineers) where people are paying, it must survive 6 months, and it must be maintainable.
3. **Program design** (what most people skip) — Decisions the agent will make that you might not like. Exactly "the inverse process" of Victor Talin's prompt ("while working on this, which choices did you make that you're not confident of?") — but done *before* the model runs, because once the model has written hundreds/thousands of lines you're deep in a context window, biased by its earlier choices, and resteeing is expensive.
   - Dylan Marcy (Cloudflare) notes most good plans end with what the tests and call stack will look like.
   - These design conversations are *very context-cheap*: his in-progress program-design session was at 43,000 tokens having already made many decisions (endpoints, flow) — so you're getting the most model intelligence for the fewest tokens, early in the context window where long-context degradation hasn't kicked in.
   - Decide where files go ("why did you put that over there?" is a cheap question to settle beforehand). Use human-readable code blocks: types and method signatures, but not implementation details, so a human can quickly judge right vs wrong.
4. **Vertical slices** (Matt Pocock talks about this; Dex did a video with him on "tracer bullets") — Models build horizontally by default (database, then services, then API, then frontend) and you end up thousands of lines later with nothing testable along the way. Instead: build a thin slice end-to-end first (mock API endpoint, stub frontend, wire it down), *test it along the way* — manually, curl, browser agents — then add logic and business cases. Get it working all the way through first, then layer in complexity. This resteeing is infinitely cheaper than at the end when the "trajectory" is wrong. It's how you learn a language (hello world, then mutate it) and how business works (first customer first).

All of this rests on the thesis: **they can solve problems really, really well, but they cannot write maintainable code without you in the loop helping.**

## Why models write slop: the RL view

- Dex dug into how reinforcement learning works to explain why quality/maintainability isn't learned. Visualization (inspired by Calvin French-Owen): the model tries a problem many times at high temperature, traces are scored, good traces are weighted up, bad ones down.
- The problem: **benchmarks carry no penalty for bad design.** SWE-bench problems are small — a golden patch of 100–200 lines, a new test that must pass. You check out the pre-fix commit, the agent patches, you discard its test edits, run your tests in a sandbox. A model could score 99% on SWE-bench and Dex "doesn't give a" — it's better at problem-solving, but nothing penalizes it for writing slop (tens of thousands of lines, pointless try/catch/log/rethrow patterns, weird type casts). You'd fire an engineer who solved a problem that way.
- Why no quality penalty? Verification in RL needs an **oracle**, and maintainability has no fast oracle. Tests run in seconds; the cost of bad architecture is measured in weeks and months — a bad decision now compounds into an incident later, and it's nearly impossible to back-propagate that through a training run. Note also that all benchmarks (even frontier ones) give the model the whole problem up front, while real software is discovered iteratively — ship, get feedback, ship again. What he'd trust: a roadmap of 20 features fed one at a time, proving the model keeps the codebase easy to change.
- A Cognition benchmark moves the right direction: humans curate issues, but importantly an LLM judge checks functional equivalence against the golden solution (don't penalize different-but-correct implementations), plus a quality judge checking rule-following, and the killer trick — **run the model's tests against the pre-patch code; if they don't fail, the tests test nothing.** This is "extracting the word *taste* into numbers, tests, and measurements."
- His caveat: model-judging-code-quality can only go so far. His unprovable-but-shared vibe: "if the model knew what good code looked like, it would write it in the first place." Throwing more tokens (e.g. Fable writes, Codex reviews) does raise the floor and catches the small stuff, but that's all.

## Context engineering (his coinage)

- The 12 Factor Agents paper (April 2025) first used "context engineering"; at least 9 of 12 factors still hold, many now free in modern harnesses. The big one: **own your context window**. Everything — RAG, history, memory, prompt design — is just tokens in, tokens out. Understanding down to the token level (e.g. XML is more token-efficient than JSON) and keeping the context right-sized ("no wrong information, no missing information, as small as possible") is the fundamental lever on results.
- The history: he published in April 2025, Karpathy and others started talking about it in June; Jeff Huber (Chroma) tweeted the two words "context engineering" weeks after the paper. Multiple parallel discovery, Newton-Leibniz style. He still jokes about tweeting Karpathy about it.
- Hard-think early: the deeper you are in a context window, the worse the model performs — so do the hard reasoning while it's cheap. Hence the program-design stage before letting the agent cook.
- **The "dumb zone"**: he coined this in a training session watching engineers push Opus sessions to ~100–120k tokens and get garbage. Practical rule of thumb for beginners: when you're around half the context window, compact everything into a document and start a fresh session from it. Experts get lazy and run 200–300k tokens, but compaction is improving. Humans have a dumb zone too — tired and cranky, results drop. Calvin French-Owen's metaphor: a student mid-exam realizes time is running out and starts scrambling and cutting corners ("context anxiety" seen in Opus 4.5/Sonnet 4.5).
- **Put everything in the repo**: his biggest contribution. The codebase is traditionally only code, but models don't know the business context: `/doc/ADR` (record decisions: why pricing is set this way, we never change the API schema, we ship v2 instead of breaking the contract), `/doc/external` (Vercel env var *names*, payment processor setup, test emails, where customers contact you) — so the model finds context deterministically via read/grep instead of MCP server instructions that burn attention. Each session can hook "pull the last 10 incidents" for free — CPU cycles, not inference. Save inference for reasoning.
- Not to be confused with *prompting*: telling the model how to do it narrows probability toward what you want; not telling it opens a broader realm — terrible ways, but also better solutions you'd never have imagined.

## The bigger picture: bottlenecks vs. inefficiencies

- "Stop playing with your coding agents and get back to work" is the office joke — it's so fun to build the thing that builds the thing. But agents are a station in a factory: **token-maxing is "there are inefficiencies that are not bottlenecks"** (from Eli Goldratt's *The Goal* — optimizing every station creates work-in-progress piling up in front of the bottleneck).
- If the bottleneck is code review or production being down, adding more coding agents or fancy multi-agent routing won't deliver value faster. Work the actual bottleneck (like Musk does), hold your nose on the rest, and let small fires burn — identify which fire is the wildfire that burns the city vs. embers to leave. It's expected-pain / probability thinking (he compares it to Starcraft: hundreds of micro-decisions with incomplete information, stacking probabilities, betting on what you've seen).
- His own history: obsessed with the dev platform / CI speed / release cadence since his first job (the guy who owned the deploy pipeline was the most important person in the company) — and repeatedly told by bosses, "stop making CI faster, ship the tickets."
- **You're not competing with Anthropic; you're competing with a PM at Anthropic.** Small founders out-execute teams inside giant orgs (Browser Use beat Anthropic's own because incumbents aren't focused on your niche). Most big-company "labs will win" talk is an excuse not to build. He builds in the vein of a world he wants to live in; founders are on the same side — founders vs. the incumbents, or vs. people who hate innovation. The space filters for true believers; many are here for hype, not belief.
- Zooming out: AI is one of the most unpopular things in the world right now, and most people's only AI experience is Google AI search plus fear of losing their job. Nobody technical-adjacent has a compelling answer for how this works out for non-technical people. His planning framework: the exponentially-good "abundance singularity" world and the "Terminator" world are both worth a probability mass, but the only world worth planning for is the **middle path** — things just keep getting better, a bit faster each year. If either extreme happens, today's work barely matters anyway.

## Core takeaways

- Agents are excellent problem-solvers but cannot produce maintainable code without the human in the loop. Plan to keep reading code (or at minimum holding grip on the product's logic) for the foreseeable future.
- Spend cheap attention up front in four stages — product (measurable outcomes), system architecture, program design (call stack/tests/files/types at ~40k tokens, before the agent cooks), and vertical slices (test a thin end-to-end slice before adding logic) — to minimize expensive resteeing later.
- Benchmarks measure problem-solving, not maintainability; there's no RL oracle for bad architecture, so trust benchmark results accordingly.
- Context engineering = owning the context window: right tokens in, as few as possible; hard-think early; compact into a doc when you hit the "dumb zone."
- The layperson's natural organizational structure for all this: the repo itself — ADRs and external-context markdown files make the environment exactly what the model is good at (read, write, edit, grep, bash).
- Don't max tokens for its own sake; find and work the real bottleneck end-to-end.
