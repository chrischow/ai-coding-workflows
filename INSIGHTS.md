# Actionable Insights: AI Coding Workflows

Synthesised from 16 summaries of practitioner workflows (Charlie Holtz, Chris Titus, Coding Sloth, Cole Medin, David Ondrej/Dex, DevOps Toolbox, IndyDevDan, Kun Chen, Matt Pocock, Milan Jovanovic, Owain Lewis, Primeagen, Tech With Tim, Web Dev Cody, Zen van Riel).

---

## Core Principles

- **Context is your scarcest resource; treat it like money.** Every file read, website fetched, and message exchanged costs tokens, and model quality degrades noticeably once a session grows deep — past roughly a fifth of the window, reasoning gets sloppy, forgetful and self-contradictory. The consistent practice is to run one focused task per fresh session, kill research tangents the moment they appear, keep prompts deliberately specific, and compact into a document and restart whenever a session approaches the danger zone. Carry state forward between sessions in written artifacts, never in long chat histories.

- **The human stays in the loop at a few manual gates.** Agents left alone drift, invent scope, and produce code that works today but is unmaintainable next month. Almost every practitioner gates the workflow at the same two points — approving a plan before implementation starts, and a real review before merging — with a QA pass on the product in between. The value of the whole exercise lives in that review loop: edge cases surface there that no prompt or spec anticipated, so review is not a formality but the core of the job. Done right, the human inspects inputs and outputs (plans, interfaces, test plans, reviews) rather than every line of implementation, reserving deep code reads for risky changes.

- **Specify intent before generating code, and reduce assumptions as early as possible.** A vague prompt hands every design decision to the agent, and agents guess. Writing a short spec first — the what and why, the constraints and out-of-scope items, the key decisions, and discrete tasks each with a verification step — turns guessing into execution. Because a wrong plan propagates far more damage than a wrong line of code, the cheapest high-leverage move is to let the agent interrogate you: answering 20–25 pointed questions up front removes assumptions and surfaces edge cases you would never have considered. The result is that most decisions are made cheaply in conversation, and only the durable artifacts (spec, PRD, glossary) survive into implementation.

- **Progressive disclosure beats dumping everything into every prompt.** Global memory files load into every session, so they must stay tiny; everything conditionally useful — e2e testing steps, component conventions, API details — moves into on-demand assets (skills, reference docs) whose full content loads only when the agent decides it needs them. A small, curated toolkit that matches your style outperforms a bloated one, and every piece of it should be vetted, since third-party skills can run arbitrary code on your machine. The same principle extends to planning: plan with a capable model, implement with a cheaper one, and never load context nobody needs.

- **Verification is a first-class step, never an afterthought.** Models cannot tell whether their own output is correct, so acceptance criteria must always include a concrete validation — a test, a type check, a lint pass, a browser run — and the strongest practice is defining the validation before writing any code. Writing tests first and letting the agent make them pass undercuts self-grading; testing against a real database instance, real API calls, or a real running app catches what mocks hide. Front-end work needs the agent to actually open the app and observe it through screenshots, and the human should still manually use the product like a user before anything ships. Assume nothing: a model that scored well on benchmarks or produced plausible-looking code has earned precisely zero trust in your particular codebase.

- **Spend cheap up-front attention to avoid expensive rework later.** Design decisions made early in a context window cost almost nothing and buy disproportionate quality: pin the architecture, decide where files live, sketch types and method signatures rather than implementations, and build a thin end-to-end slice first to prove the trajectory before layering in logic and business cases. Re-steering after the agent has written thousands of lines is orders of magnitude more expensive than settling the same questions in twenty minutes of conversation. The corollary is to be exceptionally careful about what you let the AI design: humans should own architecture, module boundaries and interfaces, while the AI gets large free-reign zones inside those contracts.

- **Invest in the layer around the code, and evolve it on every failure.** The durable asset is not any single generation of code but the memory system: global and project rules files, standardized commit messages the agent reads as long-term history, commands that encode repeatable workflows, and reference docs for each concern. Every bug, misalignment, or "I don't like how that turned out" is an opportunity to tighten that layer so the failure does not recur — rules become sharper, on-demand context grows, regression tests get added. Over time the agent becomes measurably more reliable and more in tune with how you work, which compounds: codebase, test base, and AI layer evolve in parallel.

- **What you build, not how you prompt, decides how much you can parallelise.** Many agents can work on the same codebase simultaneously without colliding, provided the code is modular: small, isolated services and per-agent worktrees mean sessions never touch the same files or panels. Clean architecture and isolation are what make concurrency work, and they are human jobs. Conversely, agent harnesses don't rescue a tangled codebase, and no amount of orchestration fixes a messy one — the same engineering discipline that enabled parallel human teams is what enables parallel agents.

- **A good workflow beats a better model, and simplicity beats cleverness.** Practitioners who ship at scale consistently describe boring, repeatable pipelines — plan, implement, verify, review, merge — executed many times rather than heroic one-shot prompt sessions. Three-act structure (engineer at both ends, deterministic code in the middle) beats elaborate multi-agent choreography: linters, type checkers, formatters and tests are code — deterministic, cheap, unhackable — and failures from them should flow back into the builder automatically. Start with the smallest workflow that solves a real problem, run it by hand first until you understand every node, and only then codify it. The bottleneck thinking applies too: don't optimise token spend or agent count for their own sake — find the actual constraint in your pipeline (often code review or production stability) and work that.

- **The tooling and environment you set up beforehand are what make builds fast.** When practitioners report "the whole app took ten prompts," the real story is hours of prior setup: research and decisions captured in a persistent document, agent skills and MCP servers installed so the model knows how to drive external services, persistent rules injected into every session, real API keys and environment values in place, and a well-chosen tool surface. Tool ergonomics matter enormously: CLIs and token-efficient output formats slash cost and latency versus verbose alternatives, and knowing the capabilities of your tools beforehand is what lets you correct the model mid-flight instead of guessing.

- **You remain the product owner; agents remain workers.** Teams that get this right spend their energy on direction — talking to users, reading the market, choosing the next move — while agents churn through execution and PRs. Voice input (speech-to-text, roughly three times faster than typing) is a common enabler for keeping that human thinking fast. And the final quality bar is always yours: run the app, feel the UX, reject what you don't like, and keep the codebase's shape something you can still reason about, because the day you stop reading code is the day you inherit a bug nobody can fix.

## Recommended Workflow

1. **Shape the idea before any code exists.** Start with a loose, messy idea, not a requirement. Research what already exists, choose the tech stack deliberately, and read the documentation for each tool so you know what it can actually do before you ask the model to use it. Use generous, unstructured input — dictating raw thoughts into a scratch session, or having the agent research and debate alternatives in a window separate from your editor — and let the AI interrogate you with questions until the scope snaps into focus. The goal of this phase is purely to shrink ambiguity; no implementation decisions should be made here that you aren't prepared to throw away.

2. **Capture the outcome as durable documents in the repo.** Convert the conversation into a product spec or PRD that states the problem, the intended users, the required behaviour, the constraints and out-of-scope items, and the success metrics — plus a shared glossary so you and the agent use the same vocabulary for the same concepts. Keep the AI's suggestions about what to build, but make the scope and decisions yours, and commit the documents. The chat that produced them is disposable; these files are the only thing that survives — they are the contract both you and any future session will work from.

3. **Break the work into tasks sized for one clean session each.** Slice the spec into discrete tasks with a rough upper bound of a single context window of work, each describing what to build, which files to touch, and how completion will be verified, sequenced with blocking relationships where needed. Merge trivial one-liner tasks into their neighbours — spinning up an agent costs the same whether the task is one line or a hundred. Record these as tickets in whatever tracker you use so the agent has a durable, resumable queue it can pull from.

4. **Set up the guardrails and the environment before building.** Write or refresh the project rules file that the agent always sees: the stack, the commands to run and test with, structure pointers, naming conventions, gotchas, and pinned versions (models default to outdated and insecure ones). Configure your curated set of skills, MCP servers and agent harness files so external services are usable without doc-paste. Prepare real environment variables, database access, and a skeleton test suite, and validate that the guardrails themselves work before any feature code starts.

5. **Plan each task twice: openly, then structurally.** For a given task, first discuss it openly with the agent — architecture options, codebase analysis via sub-agents, edge cases — then ask it to turn that conversation into a concrete task plan: problem statement, references, file-by-file changes, and a validation strategy decided before a single line is written. Review the plan for scope, interfaces, module boundaries, and decisions you might not like, and settle design choices such as where files live and what the call stack and tests will look like while the reasoning is still cheap. For anything beyond a trivial change, resist skipping this stage — it is where most mistakes are cheapest to catch.

6. **Implement in a fresh session, one task at a time, isolated from everything else.** Start a new conversation in which only the task plan is loaded, so execution begins with a clean, unbloated context. Run the agent to implement, in a dedicated worktree or sandbox when you want parallelism or safety, and delegate research to sub-agents that report back summaries instead of polluting the main context. Delegate the coding itself — this is where the agent's speed earns its keep — and resist the urge to micro-manage keystrokes; your interventions belong at the gates, not inside the task.

7. **Close the verification loop automatically before a human ever looks.** Have the agent run the full gauntlet itself: type checks, linters, unit and integration tests, then end-to-end tests against a real running instance — including browser automation for UI work, capturing screenshots as evidence. Feed every failure back into the builder until everything is green, and make sure the tests were written against the requirements, not after the fact to celebrate its own output. Real API integrations should be exercised against the actual services, and the evidence (screenshots, logs, demo video) saved where a human can inspect it.

8. **Review with fresh eyes, machine and human.** Run the work past independent reviewers in a new context — reviewer sub-agents, external tools — one check against the original spec to catch forgotten details, another against your coding standards. Then read the review comments and the interfaces yourself and decide what to accept and reject: the AI cannot reliably criticise code it just wrote in the same context it wrote it, and neither can you on the same assumptions you prompted with. Most changes are low-risk and can pass with email-level scrutiny; reserve deep, line-by-line reads for the genuinely risky ones, and review inputs and outputs rather than every implementation detail.

9. **QA the product like a user, in parallel with more fixing.** Rebuild and run the app yourself — create the account, click the buttons, walk the flows a real user would — with a checklist of what to test. This is where the true edge cases appear that no planning could have anticipated, so treat every find as data, not failure, and feed findings back as tickets. The powerful move is to run the agent's implementation loop in parallel with your QA: you keep testing while it keeps fixing, day shift and night shift compounding, so that by the time you have finished exploring one version the next iteration is already waiting.

10. **Commit, open a PR, and gate the merge manually.** Have commits made with a standardised, informative format — your commit history doubles as the agent's long-term memory of how the codebase evolved. Open a pull request as the formal handoff: wait for CI, let the independent reviewers comment, then read the code and the reviews yourself, instruct the agent to address and resolve the feedback, verify the resolution, and merge only when you are genuinely satisfied. A clean, well-reviewed history with a human merge gate is what keeps a sleep-deprived agent fleet from slowly corroding the codebase.

11. **Run the long tail of automation continuously.** Set up the boring infrastructure once: dependency scanning, static security scanning, CI that tests on every supported platform or distribution, and monitoring for production. Use scheduled agent loops for the grunt work — picking up open issues daily, sweeping for security and bug patterns, and leaving PRs and findings waiting for you — but always with caps on tokens and iterations so a runaway loop cannot burn through your budget overnight. Long-running tasks should only be given objectives that are verifiable, with a clear stop condition.

12. **Evolve the system after every cycle, then repeat.** At the end of each feature's journey, ask what the AI layer should learn from it: tighten a rule, add an on-demand reference doc, extend the regression suite, or refine a command so the misalignment cannot recur. Make those small, focused meta-changes deliberately — often by hand — while delegating the codebase work to agents. Batch this into a steady rhythm of release cycles: accumulate a week's worth of fixes and features, run the changes concurrently against main in isolated worktrees, review each one by hand, ship a release, and let on-the-fence features sit behind an experimental flag before you commit to keeping them. The compounding effect — a more reliable agent, a cleaner codebase, a sharper memory system — is what separates a workflow you maintain from a workflow that maintains you.
